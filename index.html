Agent architecture · explained without the math

How 10,000 AI agents worked on a 90-year-old math problem

In September 2026 OpenAI said a swarm of AI agents resolved the Navier–Stokes problem, one of the seven Millennium Prize questions. The papers are 220 pages of analysis. This page skips the analysis and explains the part that matters to builders: how the agents were organised, what each one could do, and how the answer was checked.

By Nikhil Mane · Diagrams generated with Archify from OpenAI's published description and the public Lean repository · Source on GitHub

In five sentences
  1. Agents were split into groups, and each group was given a different framing of the same question. Some were told to prove the fluid stays smooth, others to construct a case where it does not.
  2. Each agent ran on an internal model stronger than GPT-6 Astra, inside an isolated sandbox with two tools: a cached copy of the internet and the ability to run code. Agents talked only to their own group.
  3. A small group of about 100 agents first solved an easier, related problem (Euler) in about 50 hours. That result was fed to the main groups as a starting point.
  4. Humans did not write mathematics. They chose the framings, moved compute between groups, swapped in a newer model mid-run, and used Codex to merge the best ideas across groups and re-prompt them.
  5. The final argument was rewritten in the Lean 4 proof language and checked mechanically. Every step is machine-verified, using only three standard logical axioms.

The question, in plain words

The Navier–Stokes equations describe how fluids move: water in a pipe, air over a wing, smoke from a candle. Engineers have used them for nearly two centuries. The open question was whether a perfectly smooth flow can ever "blow up", meaning its speed becomes infinite at some point in finite time, or whether the equations always keep things smooth.

The Clay Mathematics Institute's official problem statement lists four ways to settle it. Two of them (call them A and B) mean proving that blow-up never happens. The other two (C and D) mean constructing a concrete example where it does. OpenAI's agents produced C and D: an explicit example, with a smooth external force, where the flow blows up.

That is all the mathematics you need for the rest of this page.

The architecture

Below is a system map of the run. It is interactive on desktop: click a numbered chapter at the top to walk through it, or click any box to see what it connects to. Source-linked boxes open the exact files in OpenAI's repository.

Reading the map, left to right

  1. Problem variantsThe same problem written four ways. Groups aimed at a proof (A/B) and groups aimed at a counter-example (C/D) ran side by side, so the swarm did not have to guess which direction was right.
  2. Group schedulerLaunches groups of varying sizes. The group that produced the Navier–Stokes result ran on the order of 10,000 agents at once.
  3. Agent groupsAgents exchange messages inside their group only. Keeping groups separate keeps their approaches different; no single idea can take over the whole swarm early.
  4. Frontier model + tool sandboxEvery agent is the same recipe: an internal model more capable than GPT-6 Astra, a cached snapshot of the internet to read, and a code runner to test ideas numerically. When a further-trained checkpoint became available mid-run, agents were switched to it.
  5. Euler warm-upBefore the big run, about 100 agents spent about 50 hours on the unforced Euler equations, a simpler cousin of Navier–Stokes. They found a blow-up there. That told the team which direction was promising and gave the main groups a worked example to build on.
  6. Codex consolidatorHumans used Codex to read the intermediate results from different groups, pull out the most useful insights, and write follow-up prompts that fed those insights back in. This is the only place ideas cross group boundaries.
  7. Lean formalizerOnce the argument was written up, GPT-6 Astra spent 17 hours translating it into Lean 4, a language where a computer checks every logical step. The public repository holds 2,659 Lean files and reports zero unproven gaps.
  8. Comparator checkAn independent tool replays the named theorems against a separately written statement of the problem and confirms that only three standard axioms were used. This is what makes the result checkable by anyone, without trusting the model or the authors.

Why a proof written by AI can be trusted

Language models can produce convincing text that is wrong. The reason this result is different is the last two boxes on the map.

Lean is a programming language for mathematics. A theorem written in Lean is either accepted by the checker or it is not; there is no partial credit and no room for a persuasive but broken step. The agents' 220 pages of prose were translated into Lean and the checker accepted all of it.

Comparator answers a second question: did they prove the right statement? It takes a statement of the problem written independently (adapted from Google DeepMind's Formal Conjectures project), replays the proof against it with a separate small checker, and lists the axioms used. Anyone can run it from the repository with three commands.

Status as of publication: OpenAI's repository marks the review as self-assessed. The formal check is complete and reproducible; human peer review by the mathematics community is ongoing.

What carries over to ordinary agent systems

You do not need 10,000 agents to use the ideas. Five patterns from this run apply to any team building with agents today.

Diversity by framing, not by temperature

Give separate groups genuinely different versions of the task. Different questions produce different approaches far more reliably than sampling noise does.

Isolate groups, then merge deliberately

Agents that all talk to each other converge early. Keep communication inside groups and make cross-group sharing an explicit, curated step.

Warm up on the easier cousin

A small run on a simpler related problem tells you which direction is promising and gives the main run a worked example to start from.

Humans steer, they do not solve

The human jobs were framing, compute allocation, model swaps and consolidation. Design your operator loop around those four controls.

Verify mechanically, not by reading

The output was accepted because a checker said so, not because it looked right. Wherever you can, make the final gate a machine check, not a review.
